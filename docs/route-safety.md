# Перенос маршрутов и эксклюзивность

## Исправление в 2.5.3

В 2.5.2 добавление маршрутов на новый интерфейс и удаление исходных по сохранённым index отправлялись одним пакетом RCI. Проверка ответа выполнялась после обработки пакета. Такой порядок не гарантировал сохранность исходных маршрутов при отклонении добавления или смене служебного идентификатора. Успешный HTTP-ответ также не подтверждал наличие всех перенесённых адресов.

В 2.5.3 перенос работает так:

1. Проверяется существование выбранного интерфейса и соответствие маршрутов снимку выбора в окне. Отключённый, но существующий туннель допустим; удалённый — нет.
2. До первой записи создаётся резервная копия. Ошибка диска останавливает операцию.
3. Новые маршруты добавляются отдельным запросом, без сохранения незавершённого переноса.
4. Таблица перечитывается. Проверяются адреса, интерфейсы, описания, метрики, auto, reject и включённое состояние. Конфликт с существующим маршрутом не заменяется молча.
5. Проверяется, что целевой интерфейс ещё существует, а исходные параметры не изменились. Только затем удаляются исходные маршруты по адресу/интерфейсу/шлюзу/метрике. Устаревшие index для удаления не используются.
6. После сохранения повторно проверяется результат. Выбор в интерфейсе очищается, таблица обновляется.

Операции одного клиента сериализованы. При неизвестном результате записи, например таймауте, команда не повторяется вслепую. При частичном добавлении исходные записи остаются; дополнительные копии могут быть видны до следующей проверки. Общий перенос DNS и IP не является транзакцией Keenetic: если одна часть завершена, а следующая не удалась, уже перенесённая часть остаётся на новом интерфейсе. Резервная копия содержит обе части до операции.

Копии находятся в `%APPDATA%\RouteDeck\backups` (для запуска из исходников — в папке данных программы). Формат совместим с импортом RouteDeck; дополнительное поле `ip_routes_snapshot` сохраняет также шлюзы, метрики, служебные index и маршрут по умолчанию. Обычный импорт не восстанавливает эти дополнительные поля автоматически. Не импортируйте все старые маршруты без просмотра: среди них могут быть намеренно удалённые записи.

## Когда применяется эксклюзивность

В окне параметров DNS-правила переключение флажка меняет форму. Запись на роутер происходит после «Сохранить»; «Отмена» ничего не отправляет. Перезапуск роутера не требуется. Если правило выключено, флаг сохраняется, но правило начнёт действовать после включения.

После записи RouteDeck перечитывает фактические auto, reject и включённое состояние. Отклонённое изменение не отображается как успешное; при подтверждённой ошибке восстанавливаются исходные параметры. Потерянный ответ не вызывает слепого повтора или отката.

Эксклюзивное правило направляет трафик только через выбранный интерфейс и запрещает обход, когда он недоступен. Действие DNS-маршрутов зависит также от DNS-запросов через роутер и политики подключения клиента. Проверка конфигурации в RouteDeck не является проверкой фактического сетевого трафика. См. [условия DNS-маршрутизации Keenetic](https://support.keenetic.com/skipper-dsl/kn-2112/en/51150-dns-based-routes.html).

## Проверки без изменения рабочего роутера

`tests/test_route_moves.py` моделирует RCI, который продолжает выполнять пакет после ошибки, а также переиспользование и изменение index. Старый метод 2.5.2 в этих сценариях теряет исходные маршруты; новый метод сохраняет адреса. Проверены большие группы из 1400 маршрутов, частичный выбор, исчезновение туннеля, конфликты, изменения после открытия окна и во время переноса, отказ чтения, таймаут, параллельные запросы, сбой диска, копии и откат DNS-флагов.

Браузерные сценарии проверяют галочки групп, общий перенос с фильтром исходного подключения, неизменяемый снимок выбора, ошибку переноса и сохранение/отмену/ошибку эксклюзивности. Все изменяющие запросы идут к тестовой модели, а не к рабочему роутеру.
